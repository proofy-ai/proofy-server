## 1. Proofy가 맡는 곳

### 이의제기 5단계 중 2단계

일반적인 이의제기 흐름(참고: [법률사무소 안내 글](https://www.yglaw.co.kr/bbs/board.php?bo_table=lawinfo&wr_id=27), 법령 기준 절차는 `docs/screen-flow.md`)과 Proofy의 역할이다.

| 단계 | Proofy | 비고 |
|---|---|---|
| 1 지급정지 사실 확인 | 일부(화면 2) | 통지일·공고일 입력, D-day. 사유 확인은 은행에 직접 |
| **2 소명 자료 준비** | **핵심(화면 3·4·5)** | 체크리스트, 사연–자료 대조, 소명서 초안. **AI가 일하는 곳은 여기뿐** |
| 3 신청서 제출 | 안내(화면 6) | 초안을 신청서 사유란에 옮겨 적게 안내. 은행 연동 없음 |
| 4 심사·결정 | **하지 않음** | 은행의 판단이다. 해제 가능성·결과 예측은 원칙 1 위반. 대신 2단계에서 근거를 댄 조건부 의견과 질문을 낸다(2.8) |
| 5 불수용 시 대응 | 안내(화면 6, 정적) | 법률 상담(대한법률구조공단 132) 안내 한 줄 |

### 소명 자료 3분류와 초안 구조

같은 글은 소명 자료를 세 가지로 나눈다. Proofy는 이 분류를 **초안의 묶음(`DraftSection`)** 으로 쓴다.

| 분류 | 보여 주는 것 | 초안 묶음 | Proofy에서 |
|---|---|---|---|
| 01 입금 경위 | 어디서 왜 들어온 돈인지 | `DEPOSIT_REASON` | ② 대조가 바로 이 일을 한다(사연 + 거래내역서 + 대화) |
| 02 범죄 가담 의사 없음 | 정상 거래였다는 정황 | `NO_INVOLVEMENT` | 대화·계약서·사업자등록. 문장은 **사용자 본인의 진술**로 쓰고 AI가 사실로 단정하지 않는다 |
| 03 사기 피해 경위 | 오히려 내가 피해자라는 기록 | `VICTIM_CONTEXT` | 협박 문자, 신고 기록(체크리스트 항목 `INCIDENT_REPORT`, 서류 종류는 `OTHER`). 통장 묶기(test02)의 핵심. 정황이 없으면 이 묶음은 쓰지 않는다 |

## 2. 에이전트 흐름

```text
POST /analysis-runs (202, answers가 있으면 먼저 저장) → 백그라운드 실행, 마감 150초
  ① EXTRACTING  [코드]      글자 추출 → 마스킹(서류 줄, 사연, 지금까지의 질문·답)
  ①-b           [코드]      거래내역서 → 거래 행 (규칙 파싱, T15 결정 1)
  ⓪ SAFETY      [코드]      상담 안내 표현 찾기(부정문 제외) → 찾은 부분을 ②에 "확인할 표현"으로 넘김
  ② COMPARING   [AI 도구 루프] 사연·답 ↔ 자료 대조, 법령 조회 → findings, AI 권장 자료,
                             의견·질문, 상담 권유 여부(사연·답 원문 인용)
  ③ DRAFTING    [AI 1회]    findings만 가지고 초안 문장 + 근거 번호 + 묶음 (상담 권유면 건너뜀)
  ④ VERIFY      [코드 → AI 1회 → 코드] 초안 문장·의견 후검증, 고칠 수 있는 것만 AI가 1회 고쳐 쓰고 재검증
  ⑤ 결과        → 사용자가 질문에 답하고 "답하고 다시 분석" → 처음부터 다시(답은 ①에서 함께 가림)
```

화면 단계(`stages`)는 ①·②·③ 세 개다. ⓪과 ①-b는 ①에, ④는 ③에 포함해 보여 준다. 각 단계에서 한 일은 `steps`에 한 줄씩 남는다(계약 4.10). 가짜 분석·미리 만든 결과에서는 ⓪의 표현 목록만으로 상담 안내를 정한다.

**자율과 검증의 나눔(11/22, "탐색은 자유, 결과는 엄격")**: 무엇을 조회할지, 어떤 법령 조항을 읽을지, 무엇을 물을지, 상담을 권할지는 AI가 정한다. 코드는 AI가 **지어낸 것**만 걸러 낸다: 가리기(대회 규정 제7조), 금액·날짜 계산과 대조, 인용 원문 대조(사연·답·서류·법령), 결과 예측 표현 검사.

아래 예시는 체험 계정 test01(물품 거래)이다. 사연 "11월 8일 거래처에 가죽 지갑 3개를 15만 원에 납품하고 대금을 받았습니다", 거래내역서(11/8 입금 150,000원), 판매 채팅("3개 12만원에 할게요", 일부러 어긋나게 만든 자료).

### 2.1 ⓪ SAFETY — 상담 안내 (T10, 코드 목록 + AI 문맥 확인)

- 코드가 가린 사연과 답을 정해 둔 표현 목록(통장·계좌·체크카드 대여·양도, 비밀번호 전달, 환전·구매대행·송금 알바, 현금 인출 후 전달 등)으로 찾는다. 걸린 곳 바로 뒤에 부정하는 말(`적이 없`·`지 않`·`않았`·`거절`·`거부`)이 있으면 뺀다.
- **실제 분석(`claude`)**: 찾은 부분을 ② 대조 에이전트에 "확인할 표현"으로 넘긴다. 에이전트가 문맥을 읽어 상담을 권할지 정하고(목록에 없는 표현도 권할 수 있다), 권하면 **사연·답 원문 인용**과 어떤 상황이었는지 묻는 질문을 낸다. 서버는 인용이 가린 사연·답에 있는지 확인하고, 확인된 인용만 `matchedPhrases`로 쓴다. 확인된 인용이 없으면 코드 목록이 찾은 부분을 쓰고, 그것도 없으면 상담 안내를 띄우지 않고 step `VERIFY`에 남긴다.
- **가짜 분석·미리 만든 결과**: 코드 목록에 걸리면 상담 안내. AI를 부르지 않는다.
- 상담 안내로 끝나면 `SUCCEEDED`, `result.referral` + `agentReview`(질문), 초안 없음(이전 초안 삭제). step `SAFETY`(예: "사연의 '체크카드를 건넸고'를 문맥으로 확인 → 상담 안내", "'통장을 빌려'는 '빌려준 적이 없다'는 뜻이라 상담 안내 안 함").
- 사람을 판정하는 것이 아니라 상담이 먼저 필요해 보이는 표현이 있음을 알린다. 사용자가 질문에 답해 상황을 설명하고 다시 분석하면 에이전트가 다시 본다.

### 2.2 ① EXTRACTING — 글자 추출과 마스킹 (T13·T14, 코드)

| 입력 | 처리 | 출력(DB) |
|---|---|---|
| 올린 서류(PDF·PNG·JPG) | 글자가 든 PDF는 OCR 없이 추출(`pypdf`). 사진·스캔 PDF는 전처리 후 Tesseract OCR | `evidence.regions_json` 줄 단위 `{index, page, text, bbox, confidence}` |
| 추출한 글자 | 주민번호·계좌·전화·이름을 가림(`김민수` → `김*수`) | `evidence.masked_text`, 영역마다 `maskedText` |
| 사연 | 같은 규칙으로 가림(분석 시작 때) | `analysis_runs.masked_narrative` |

- 못 읽은 서류는 `FAILED`로 두고 분석을 계속한다. 결과의 `unreadEvidence`로 "직접 확인"에 넘긴다.
- **AI에는 마스킹한 글자만 간다.** 원본 이미지는 외부로 보내지 않는다. 인용 검증도 마스킹본 기준이다(AI가 본 글과 대조해야 하므로). 서류는 `regions_json[].maskedText`, 사연은 `masked_narrative`와 대조한다(`docs/erd.md` 3.7).
- **가리는 규칙(T14, `app/agent/masking.py`)** — 외부 AI 없이 규칙으로만 가린다. 번호는 모양으로 찾는다: 주민번호는 전부, 사업자번호는 전부, 전화·계좌는 끝 4자리만 남긴다. 금액·날짜·시각은 그대로 둔다. 이름은 **사건 이름 목록**으로 찾는다. 한 사건의 서류에서 `예금주`·`대표자`·`성명` 뒤의 이름, 거래내역 행의 거래상대 칸, 사연의 `○○○ 씨`를 모은다. 이 목록의 이름을 그 사건의 모든 서류 줄과 사연에서 띄어쓰기를 무시하고 가린다. 서류가 바뀌면 목록도 바뀌므로 실행마다 사건 전체를 다시 가린다. 한 글자 틀리게 읽은 이름(OCR)은 찾지 못한다(T14 결정 5). 가린 글은 `MaskedText` 타입이고 `agent/llm.py`(T16)는 이 타입만 받는다.
- 시연 서류는 글자가 든 PDF로 만든다(T12). 대조 품질이 거래내역서 인식에 달려 있기 때문이다. 사진 OCR은 Docker 이미지에서 동작을 확인한다.

### 2.3 ①-b 거래 행 추출 (T15, 코드 규칙)

- **AI를 부르지 않고 코드 규칙으로만 뽑는다**(11/22 T15 결정 1). 금액·날짜를 코드가 만들고(원칙 2), 시연 거래내역서는 글자가 든 PDF라 규칙으로 정확히 나온다. AI 추출(규칙이 못 찾은 서류만 다시 뽑기)은 시간이 남으면 T19에서 본다.
- 규칙(`app/agent/transactions.py`, 모양은 `app/agent/masking.py`의 `TX_ROW`와 같음): 한 줄이 `날짜 (시각) 입금|출금 금액 (잔액) 거래상대`이면 행이다. 날짜는 `-`·`.`·`/` 구분, 시각·잔액은 없어도 된다. 날짜·방향·금액은 원문 줄에서, 거래상대는 가린 줄(`maskedText`)에서 가져온다. `체크카드 결제` 같은 적요도 거래상대 칸에 넣는다(결정 2).
- **코드 검사:** 금액·날짜 문자열이 그 줄에 실제로 있는 행만 `transactions`에 저장한다(`row_matches_source`). AI가 행을 고르게 되면 같은 검사를 쓴다.
- `AGENT_LLM=claude`(실제로 서류를 읽는 모드)에서만 동작한다. 행 수는 step `OCR` "거래내역 행 정리"에 남기고, 못 찾으면 그 step을 `FAILED`로 남기고 계속한다. 가짜 분석기는 실제 행이 있으면 정해 둔 행을 넣지 않는다.

### 2.4 ② COMPARING — 대조 (T16, AI 도구 루프)

AI에게 거래내역을 통째로 주지 않고 **조회 도구**를 준다.

| 도구 | 인자 | 돌려주는 것 |
|---|---|---|
| `get_transactions` | `reason`, `from`, `to`, `direction?`, `counterparty?`, `minAmount?`, `maxAmount?` | 이 사건의 거래 행 `{transactionId, occurredAt, direction, amountKrw, counterparty(가림)}` |
| `get_evidence_regions` | `reason`, `evidenceId`, `page?` | 이 사건 서류의 줄 `{regionIndex, page, text(가림)}` |
| `search_law` (v0.8, T23) | `reason`, `query` | 법령에서 낱말이 맞는 조항 목록 `{ref, label, snippet}`(법률·시행령·별지 제4호, `docs/legal/` 원문을 조항 단위로 나눔) |
| `get_law_article` (v0.8, T23) | `reason`, `ref` | 조항 원문 전체 `{ref, label, text}` |

- 법령 조회는 RAG다. 법령 전체를 첫 메시지에 넣지 않고 AI가 필요할 때 찾아 읽는다. 법령은 개인정보가 없는 공개 글이라 가리지 않는다. 서버는 이번 실행에서 실제로 돌려준 조항(`ref`)을 모아 두고, 의견·질문의 근거 조항 인용을 그 원문과 대조한다(2.8).
- 첫 메시지: 사연(가림), **지금까지의 질문·답(가림, v0.8)**, ⓪이 찾은 확인할 표현, 사용자가 말한 입금(유형·금액·일자), 서류 목록(`evidenceId`, `docType`, 쪽 수, 앞부분 몇 줄).
- **`reason`(조회 이유 한 문장)은 필수 인자다.** 서버는 이를 step `TOOL_CALL`의 `summary`로 남긴다: "사연의 11월 8일 대금 입금을 확인하려고 11/1~11/10 입금을 조회 → 2건". 4번 화면에서 AI가 스스로 무엇을 왜 찾는지가 보인다.
- 도구는 **이 사건 소속 행만** 조회한다. 서버는 도구가 실제로 돌려준 거래 ID를 모아 둔다(후검증 기준, `analysis_runs.steps_json`).
- 상한: 도구 호출 12회(법령 조회가 더해져 T23에서 8회 → 12회, 모델 요청 14회), 도구 결과 60,000자(넘으면 앞부분만 주고 범위를 좁혀 다시 조회하라고 알림). 넘으면 지금까지 본 자료로 답하게 한다.
- 최종 출력(구조화, `output_config.format`):

```text
findings[]        = { claim, status: MATCH | CONFLICT | STATEMENT_ONLY | UNKNOWN, note,
                      conflict: { field: AMOUNT | DATE | COUNTERPARTY | OTHER, statement, found } | null,
                      sources[]: { kind: NARRATIVE | EVIDENCE | TRANSACTION, quote?, evidenceId?, regionIndex?, transactionId? } }
recommendedDocs[] = { label, reason, acceptedDocTypes[] }   → 체크리스트 AI_RECOMMENDED
opinions[]        = { text, findingIndexes[], lawRefs[]: { ref, quote } }        (v0.8, 0~3개)
questions[]       = { text, why, findingIndexes[], lawRefs[] }                   (v0.8, 0~3개)
consult           = { recommend, quotes[](사연·답 원문), reason }                (v0.8, 상담 권유)
```

- **판정 필드는 스키마에 없다**(해제 가능성, 수용 여부, 위험도 등). 프롬프트로만 막지 않는다.
- test01 예시 결과: f1 "15만 원 입금" `MATCH`(t3) · f2 "15만 원에 합의" `CONFLICT`(채팅 12번 줄 "3개 12만원에 할게요") · f3 "다음 날 택배" `STATEMENT_ONLY`. f2는 step `CONFLICT`로 바로 보인다. **시연의 핵심 장면**이다.
- 대조 결과 검증(코드, 저장 전):
  - 인용문이 그 서류 줄의 마스킹본(또는 마스킹한 사연)에 공백을 무시하고 들어 있나 → 아니면 `verified: false`(흐리게 표시, 지우지 않음)
  - `evidenceId`·`regionIndex`가 이 사건에 있나, `transactionId`가 이번 실행의 도구가 돌려준 ID인가 → 아니면 그 근거를 빼고 step `VERIFY`에 남긴다. 근거가 하나도 남지 않은 `MATCH`는 `UNKNOWN`으로 바꾼다
  - 글자 수 상한으로 자른다(긴 출력 유도 방지)

### 2.5 ③ DRAFTING — 초안 (T17, AI 1회)

- 입력: 검증을 통과한 findings(번호로), 입금 유형, 묶음 규칙.
- 출력(구조화): `sentences[] = { section: DraftSection, text, findingIds[] }`. `findingIds`는 **준 번호만 고를 수 있게 enum으로 고정**한다.
- 묶음 순서: `DEPOSIT_REASON` → `NO_INVOLVEMENT` → `VICTIM_CONTEXT`(정황이 있을 때만). `NO_INVOLVEMENT` 문장은 1인칭 진술("본인은 … 알지 못했습니다")로 쓰게 한다.
- 문체: 은행에 내는 존댓말 서술. 판정·예측 표현 금지.

### 2.6 ④ VERIFY — 후검증과 1회 고쳐 쓰기 (T17, 코드 → AI → 코드)

문장마다 검사하고, 걸린 문장은 `needsCheck: true` + 사유(계약 `NeedsCheckReason`, 앞의 것 하나).

| 검사 | 사유 | AI가 고쳐 쓸 수 있나 |
|---|---|---|
| CONFLICT 항목에 연결됐거나, 문장 속 금액·날짜가 CONFLICT 항목의 진술 값과 같음(서버가 연결을 붙임) | `CONFLICT` | 아니요. 사용자가 사실을 확인할 일 |
| 근거 번호가 없음 | `NO_SOURCE` | 아니요. 고치게 하면 근거를 지어낼 수 있음 |
| 근거의 인용이 원문에 없음 | `QUOTE_NOT_FOUND` | 아니요 |
| 문장 속 숫자가 인용한 근거에 없음 ("30만 원" → 300000으로 읽어 비교) | `NUMBER_MISMATCH` | **예** |
| 판정처럼 읽히는 표현("해제될 것", "확실히", "승인") | `JUDGMENT_EXPRESSION` | **예** |
| 근거 서류를 못 읽음 | `SOURCE_UNREAD` | 아니요 |

- **1회 고쳐 쓰기:** `NUMBER_MISMATCH`·`JUDGMENT_EXPRESSION`에 걸린 문장이 있고 마감까지 40초 이상 남았으면, 그 문장들만 오류 사유와 함께 AI에 다시 보내 고쳐 쓰게 한다(같은 `findingIds` 유지). 다시 검사해서 통과하면 고친 문장을 쓰고, 또 걸리면 **원래 문장을 두고** "확인 필요"로 표시한다. 문장을 지우지 않는다.
- step `VERIFY`: "근거와 다른 숫자 1개를 AI가 고쳐 다시 확인했습니다", "확인 필요 문장 2개".
- 어느 문장에도 연결되지 않은 CONFLICT → `draft.warnings`(`CONFLICT_NOT_IN_DRAFT`).
- **의견(v0.8)도 같은 방식으로 검사한다**: 근거 조항 인용이 이번 실행에서 읽은 조항 원문에 없음(`verified: false`), 결과 예측 표현, 근거에 없는 금액·날짜 → `needsCheck: true`. 결과 예측·숫자는 초안 문장과 같은 1회 고쳐 쓰기 호출에 함께 넣어 고치게 한다. 질문은 표시만 하고 고쳐 쓰지 않는다(묻는 문장이라 사실을 단정하지 않는다). 결과 예측 표현 검사는 초안의 판정 표현 검사(`_JUDGMENT`)를 같이 쓴다.
- 체크리스트 충족 여부는 코드가 계산한다(유형별 목록 상수 × 올린 서류 `docType`).

| 상황 | 처리 |
|---|---|

### 2.8 AI 의견·질문과 답변 (v0.8, T24·T25)

**의견(`opinions`)** — ② 대조 에이전트가 findings와 함께 낸다. 기댄 사실과 조항을 밝힌 조건부 문장이다.
- 형식: "말씀하신 내용과 [자료]를 기준으로 보면, [사실]은 [법령상 사유]로 설명할 수 있는 사정으로 보여요." 근거는 findings 번호와 법령 인용(`lawRefs`)으로만 단다.
- 하지 않는 것: 결과 예측("해제될 것", "가능성이 높다", "받아들여질 것"), 확정("~에 해당합니다"), 사람에 대한 평가. 결과 화면에만 보이고 **초안에는 넣지 않는다.**
- 서버가 `lawRefs[].ref`에 화면 이름(`label`, 예: "법 제7조 제1항 제2호")을 붙이고, 인용이 그 조항 원문에 있는지 확인한다(`verified`).

**질문(`questions`)** — 소명에 부족한 사실을 묻는다. `why`에 왜 묻는지를 쓴다.
- 무엇을 묻나: `CONFLICT` 항목의 설명(예: "12만 원과 15만 원이 다른 이유"), `STATEMENT_ONLY` 항목을 뒷받침할 자료(예: "택배 송장이 있나요?"), 별지 제4호 이의제기 사유에 필요한데 사연에 없는 사실, 상담 권유일 때 어떤 상황이었는지.
- 이미 답한 질문(`answered`)은 다시 묻지 않는다. 답으로 해결되지 않았으면 더 구체적으로 묻는다.
- 서버는 질문을 실행별로 저장하고 `questionId`를 붙인다(`analysis_questions`, ERD 3.11).

**답변 반영(`answers`, T25)** — 사용자가 답하고 다시 분석하면:
1. 서버가 답을 그 질문 행에 저장한다(같은 질문에 다시 답하면 덮어씀). `inputVersion` +1
2. ①에서 사연과 함께 **지금까지의 모든 질문·답**을 가린다. 답의 이름도 사건 이름 목록으로 가린다
3. ② 에이전트는 답을 사용자 진술로 보고 다시 대조한다. 답을 인용한 근거는 `NARRATIVE`로 저장하고, 인용 검증 기준(`masked_narrative`)에 질문·답 묶음을 붙여 둔다
4. ③ 초안은 답의 사실도 본인 진술로 쓴다("이후 1개를 추가 주문받아 15만 원이 되었습니다")
- 매번 처음부터 다시 분석한다(실시간 채팅이 아니다). 단계마다 같은 검증을 거치므로 답 때문에 검증이 느슨해지지 않는다.

**가짜 분석(`scripted`)** — 시나리오별로 정해 둔 의견·질문을 낸다. 답 내용은 읽지 않고, 답한 질문은 `answered`로 옮기고 같은 질문은 다시 내지 않는다.

## 3. 왜 이 형태인가

- **AI가 필요한 곳에만 AI.** 자유 서술한 사연과 비정형 서류(채팅 캡처, 거래내역)를 맞대어 보는 일은 규칙으로 못 한다 → AI. D-day·금액 비교·체크리스트 충족처럼 틀리면 안 되는 계산 → 코드.
- **AI가 스스로 판단하는 부분은 ②에 모았다.** 어느 기간·상대를 조회할지, 어느 서류·법령 조항을 더 읽을지, 무엇을 물을지, 상담을 권할지는 모델이 고른다. 나머지는 코드라 시연이 흔들리지 않는다.
- **묻는 에이전트로 바꿨다(11/22).** 한 번 결과를 내고 끝나는 구조는 에이전트의 언어 상호작용 능력을 쓰지 못했다. 사용자의 사연은 대개 불완전하고, 무엇이 빠졌는지는 자료와 법령을 함께 본 AI가 가장 잘 안다. 질문 → 답 → 다시 분석으로 초안의 "확인 필요"가 줄어든다.
- **법령은 도구로 찾게 했다(RAG).** AI가 법을 지어내는 것을 막고, 인용을 원문과 대조할 수 있다. 다만 법령을 안다고 판정해도 되는 것은 아니다: 법은 기준을 알려 줄 뿐 사용자의 말이 사실인지는 알려 주지 못하고, 결과는 은행이 우리가 모르는 사정(수사기관 의견 등)까지 보고 정한다. 그래서 의견은 "말씀하신 내용과 자료를 기준으로"라는 조건을 달고, 결과는 예측하지 않는다.
- **판정 없음을 스키마로 보장한다.** 출력 스키마에 판정 필드(해제 가능성 등)가 없다. 의견은 문장이고, 결과 예측 표현은 코드가 검사한다.
- **독립된 원문이 있어야 검증이 된다.** Claude 비전으로 서류를 바로 읽히면 "AI가 읽은 글"과 "AI가 인용한 글"을 같은 AI가 만들어 검증이 순환한다. 로컬 추출 글자가 기준이 된다.
- **도구 루프라서 "조회한 거래만 인정" 검증이 된다.** 거래내역을 통째로 주면 더 빠르지만 AI가 본 것과 안 본 것을 구분할 수 없다.
- **"원장"은 사용자가 낸 거래내역서다.** 신청인은 은행 원장을 볼 수 없다. 오픈뱅킹·마이데이터 연동은 확장 항목(`transactions.source`)이다(`docs/erd-review.md`).
- **LangGraph 같은 프레임워크를 쓰지 않는다(11/21 결정).** 흐름이 정해진 한 줄이고 고리는 ② 도구 루프와 ④ 1회 고쳐 쓰기뿐이라 직접 짠 코드가 짧다. 루프 안에 step 기록·호출 상한·마감·조회 ID 수집을 끼워야 하고, 외부 AI 호출이 `agent/llm.py` 한 곳이어야(원칙 4) 전송 경로를 보여 줄 수 있다. 의존성을 늘리면 이 PC의 애플리케이션 제어와 시연 안정성에도 위험이 된다.

## 6. 가져오는 코드

### 기준

- 대회 기준(안내문 3-(2), AI 활용 기준 제6조): 타 대회 출품작이 아니면 기존 코드를 쓸 수 있고, **범용 코드는 출처와 활용 범위를 공개**한다. corebank·DonWorry는 이용 권한이 있고 다른 대회에 낸 적이 없다(11/21 사용자 확인). 두 레포 모두 LICENSE 파일은 없다.
- CLAUDE.md 원칙 6: 범용 유틸(OCR 전처리, API 재시도·비용 계산 등)은 가져온다. **에이전트 흐름·검증·프롬프트는 새로 작성한다.** 두 레포 모두 기관(은행 심사자, 가맹점 보안 직원)이 판정하는 도구라 출력 구조부터 다르다.

## 7. 한계와 대응 (소개서 "AI 결과의 한계"에 그대로 쓸 것)

| 한계 | 대응 |
|---|---|
| OCR 오인식(사진 각도, 조명, 손글씨, 표 형태 거래내역 캡처) | 텍스트 PDF는 OCR 생략, 전처리, 신뢰도 낮은 영역 수 표시, 못 읽은 서류는 숨기지 않고 "직접 확인". 거래 행은 금액·일자 문자열이 원문에 있을 때만 저장 |
| 모델이 없는 사실을 씀 | 인용 원문 대조, 조회 안 한 거래 ID 제거, 문장 속 숫자 대조 → 실패 문장은 1회 고쳐 쓰고, 그래도 실패하면 "확인 필요" |
| 자료와 어긋난 내용이 초안에 그대로 들어감 | CONFLICT 연결·진술 값 일치 문장 자동 "확인 필요", 설명 안 된 CONFLICT 경고, 문장별 "직접 확인", 복사·저장 전 확인창(거짓 이의제기 처벌 안내) |
| 판정처럼 읽히는 문장 | 스키마에 판정 필드 없음 + 판정 표현 검사(조회 이유 문장 포함) + 화면 고지(`aiNotice`) |
| 기한 오산 | AI가 계산하지 않음. 공고일 없으면 "공고일 확인 필요", 있어도 "참고 계산, 은행 확인" |
| 서류 기준이 기사·보도자료 몇 건뿐 | 공식(법령)·유형별 안내(기사)·AI 분석용·있으면 좋은 자료·AI 권장을 체크리스트에서 구분해 표시 |
| 통장 대여·송금 대행처럼 처벌 위험이 먼저인 사안 | 표현 목록이 찾고 AI가 문맥으로 확인하면 초안 대신 법률 상담 안내 + 상황을 묻는 질문. 걸린 표현(원문 인용 확인)을 보여 주고 판정하지 않음. 부정문은 걸지 않음 |
| AI 의견이 판정·예측처럼 읽힘 | 조건부 형식, 결과 예측 표현 검사 → 1회 고쳐 쓰기 → 그래도 걸리면 "확인 필요". 근거 조항 인용은 원문 대조. 의견은 초안에 넣지 않음. 카드에 "변호사가 아니며 해제 여부는 은행이 판단" 고지 |
| 사용자가 답으로 사실과 다른 말을 함 | AI는 답을 사용자 진술로만 다룬다(자료 근거가 아님). 진술만 있는 내용은 `STATEMENT_ONLY`, 초안은 "확인 필요"와 복사 전 확인창(거짓 이의제기 처벌 안내) 그대로 |
| 개인정보 | 신분증 미수집, 원본 이미지 외부 전송 없음, 마스킹한 글자만 AI로, 신청인 인적사항 미저장, 24시간 자동 삭제, 시연은 합성 데이터만 |
| AI 거절·장애 | 서버측 fallback, 샘플은 미리 만든 결과로 대체, scripted 모드 |

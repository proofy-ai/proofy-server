# T15 거래 행 추출

- 단계: 3단계 실제 AI · 예정: 11/22 낮 · 상태: 완료 · 이슈: #17 · PR: #55

## 범위

- 거래내역서 → 거래 행(`transactions` 테이블): 날짜·방향·금액·상대방
- AI 1회 호출로 추출하되 금액·날짜 문자열이 원문에 실제로 있는 행만 저장
- 늦어지면 텍스트 PDF 규칙 파싱만

## 제외

- 없음

## 완료 조건

- T12 거래내역서에서 문제된 입금 행이 나옴

## 구현 계획

### 하는 일 한 줄

거래내역서에서 읽은 줄 가운데 `날짜 (시각) 입금/출금 금액 (잔액) 거래상대` 모양인 줄을 **코드 규칙으로** 거래 행으로 바꾼다. 결과는 `out.transactions`에 넣고, 저장(`transactions` 테이블)은 지금 있는 코드(`services/results.py`)가 한다. 대조 단계(T16 Claude, 지금은 가짜 분석기)는 이 행을 조회해 쓴다.

### 왜 AI 대신 규칙인가 (정할 것 1)

- 범위에는 "AI 1회 호출로 추출, 늦어지면 텍스트 PDF 규칙 파싱만"이라고 적었다. AI 호출 통로(`agent/llm.py`)는 T16에서 만들기 때문에 지금 AI 추출을 넣으려면 T16 일부를 당겨 와야 한다
- 금액·날짜는 코드가 만든다는 원칙 2에 규칙 쪽이 더 맞다. 매번 같은 결과가 나오고 비용·시간이 들지 않는다
- 시연 거래내역서(T12)는 글자가 든 PDF라 규칙으로 행이 정확히 나온다(아래 테스트 1)
- 단점: 은행마다 다른 표 모양, 사진으로 찍은 거래내역서처럼 규칙에 맞지 않는 줄은 거래 행이 되지 않는다. 이때는 step에 "거래 행을 찾지 못함"을 남기고, 대조 단계는 거래 행 없이 진행한다

### 규칙

| 칸 | 받는 모양 | 예 |
|---|---|---|
| 날짜 | `2026-11-08`, `2026.11.08`, `2026/11/08` (+ 시각 `14:22`, `14:22:05` 있어도 됨) | |
| 방향 | `입금` → `IN`, `출금` → `OUT` | |
| 금액 | 방향 뒤 첫 숫자(쉼표 허용, 1 이상) | `150,000` → 150000 |
| 잔액 | 다음 숫자(없어도 됨, 저장 안 함) | |
| 거래상대 | 나머지 글. **가린 줄(`maskedText`)에서 가져온다**(`김*수`). `체크카드 결제` 같은 적요도 그대로 넣는다(정할 것 2) | |

- 머리 줄(`거래일시 구분 거래금액…`), `조회기간 2026-11-01 ~ 2026-11-14`, `조회기간 내 거래 3건`은 모양이 달라 걸리지 않는다
- `raw_text`에는 원문 줄(서버 안에서만 씀, ERD 3.4), `region_index`에는 실제 줄 번호(샘플은 7·8·9)
- 규칙으로 뽑은 줄이라 "금액·날짜 문자열이 원문에 있다"는 저장 조건(ERD 3.4)은 항상 맞는다. 그래도 저장 전에 금액·날짜 문자열이 그 줄에 있는지 확인하는 함수를 둔다. T16에서 AI가 행을 고를 때도 같은 검사를 쓴다

### 언제·어디서

1. runner ① 단계: 서류 읽기(T13) → 가리기(T14) → **거래 행 뽑기(T15)** → 분석기. `docType=TRANSACTION_RECORD`이고 읽기에 성공한 서류만 본다. 실제로 서류를 읽는 `AGENT_LLM=claude`일 때만 동작한다(가짜 모드는 서류를 읽지 않으니 지금처럼 정해 둔 행을 쓴다)
2. 열쇠(`key`)는 `t1`, `t2`, … (사건 안에서 줄 순서대로)
3. step: `OCR` 종류로 "거래내역 행 정리 · 거래 3건(입금 2, 출금 1)을 찾았습니다." 못 찾으면 "거래 행을 찾지 못했습니다. 결과에서 직접 확인해 주세요."(`FAILED`) (정할 것 3)
4. 가짜 분석기: 실제로 뽑은 행이 있으면 정해 둔 가짜 행을 넣지 않는다. 가짜 분석기는 행을 열쇠가 아니라 날짜·금액으로 찾으므로(`_query`) 실제 행으로도 그대로 동작한다. 이렇게 하면 T11의 "샘플용 미리 만든 결과"도 실제 행 위에서 만들어진다

### 테스트 (`tests/test_t15_transaction_rows.py`)

1. **완료 조건:** test01 거래내역서 → 3행(11/03 입금 32,000 `박*진`, **11/08 입금 150,000 `김*수`**, 11/10 출금 45,000 `체크카드 결제`), 줄 번호 7·8·9. test02 → 2행(11/09 출금 23,000, **11/12 입금 100,000 `이*호`**)
2. 다른 모양: `2026.11.08` 날짜, 시각 없음, 잔액 없음도 행이 됨
3. 행이 아닌 줄(머리 줄, 조회기간, 건수 줄, 대화 문장)은 행이 되지 않음
4. `raw_text`는 원문(`김민수`), `counterparty`는 가린 값(`김*수`)
5. 연결: `AGENT_LLM=claude`로 test01 분석 → DB `transactions`가 실제 줄 번호(7·8·9)로 저장되고, 결과 탭 A의 일치 항목 거래 근거가 `2026-11-08`·`150000`·`김*수`
6. 가짜 모드 결과는 그대로(기존 T08 테스트가 확인)

### 정할 것 (추천안 먼저)

1. **뽑는 방법** — 추천: 규칙만(위 이유). 다른 안: T16에서 `llm.py`를 만든 뒤 규칙이 행을 하나도 못 찾은 서류만 AI로 다시 뽑기(시간이 남으면 T19에서)
2. **`체크카드 결제` 같은 적요를 거래상대로 넣을지** — 추천: 넣는다(가린 글이라 개인정보 문제 없고, AI가 "카드 결제로 나간 돈"을 구별할 수 있음). 지금 가짜 분석기는 `null`인데, 실제 행에서는 글이 들어간다. 화면은 `counterparty`를 문자열로 그대로 보여 주므로 FE 수정은 필요 없다
3. **step 종류** — 추천: 계약 2절에 있는 `OCR`을 쓴다(새 종류를 만들면 계약을 바꿔야 함). 다른 안: step을 남기지 않음

## 결정

11/22 사용자 확인("추천안대로 진행해"): 정할 것 1~3 모두 추천안.

1. 거래 행은 코드 규칙으로만 뽑는다. AI 추출은 하지 않는다. 규칙이 행을 못 찾은 서류를 AI로 다시 뽑는 안은 시간이 남으면 T19에서 본다
2. `체크카드 결제` 같은 적요도 가린 글 그대로 거래상대 칸(`counterparty`)에 넣는다
3. step 종류는 계약에 있는 `OCR`을 쓴다

## 결과

- 구현: `app/agent/transactions.py`(`parse_rows`, `row_matches_source`). runner ① 단계에서 읽기(T13) → 가리기(T14) → 거래 행 뽑기 순서. step `OCR` "… 거래내역 행 정리 · 거래 3건(입금 2, 출금 1)을 찾았습니다." 가짜 분석기는 실제 행이 있으면 정해 둔 행을 넣지 않는다. 표·계약 변경 없음
- **테스트가 잡은 문제:** 잔액 칸이 없는 행이면 T14 마스킹이 거래상대 이름을 모으지 못해 `counterparty`에 원문 이름이 들어갔다. 거래 행 모양 규칙을 `masking.TX_ROW` 하나로 합쳐 두 곳이 같은 규칙을 쓰게 고쳤다(잔액은 없어도 됨)
- 바뀐 기존 테스트: `test_t13_extraction.py`의 OCR step 수 세기를 서류 읽기 step(제목 "… 읽기")만 세도록 고침(거래 행 정리 step도 `OCR` 종류라서)
- 테스트: `tests/test_t15_transaction_rows.py` 6개(계획 1~5). `uv run python -m pytest -q` → 137 passed, 2 skipped(3회 연속), `uv run ruff check .` 통과
- 완료 조건 확인: test01 → 11/08 입금 150,000 `김*수`(8번 줄), test02 → 11/12 입금 100,000 `이*호`(8번 줄). `AGENT_LLM=claude` 분석에서 실제 줄 번호(7·8·9)로 저장되고 탭 A 일치 항목의 거래 근거가 됨
- 남은 위험: 은행마다 다른 표 모양(입금액·출금액 칸이 따로 있는 표, 사진 캡처)은 행이 나오지 않을 수 있다. 이때 대조는 거래 행 없이 진행되고 step이 `FAILED`로 남는다

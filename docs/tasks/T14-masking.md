### 가리는 규칙 (외부 AI 없이 규칙으로만. 가리기 전 글자를 AI에 보낼 수 없으니 AI에 이름 찾기를 맡길 수 없다)

| 대상 | 찾는 방법 | 예 |
|---|---|---|
| 주민등록번호 | `6자리-7자리` | `990101-1234567` → `******-*******` |
| 전화번호 | `01x-xxxx-xxxx`, `0x-xxx(x)-xxxx` | `010-0000-4821` → `010-****-4821` |
| 사업자등록번호 | `3-2-5자리` | `123-45-67890` → `***-**-*****` |
| 계좌번호 | 하이픈으로 이은 숫자 묶음, 숫자 합계 10~14자리(날짜 `2026-11-08`은 8자리라 빠짐) | `999-0000-1234-56` → `***-****-**34-56` |
| 이름 | **사건 이름 목록** (아래) | `김민수` → `김*수`, `정하늘입니다` → `정*늘입니다` |

- 금액(`150,000`)·잔액·날짜·시각은 그대로 둔다. 대조에 필요하다.
- **사건 이름 목록:** 한 사건의 모든 서류에서 ① `예금주`·`대표자`·`성명` 뒤의 2~4글자 한글(결정 1), ② 거래내역 행(`날짜 시각 입금/출금 금액 잔액 거래상대`)의 거래상대 칸이 2~4글자 한글이면 이름으로 모은다(`체크카드 결제`처럼 띄어 쓴 적요는 제외). 그다음 이 목록의 이름을 **그 사건의 모든 서류 줄과 사연**에서 가린다. 그래서 거래내역서에서 찾은 `김민수`가 대화 제목 `김민수 (거래처)`에서도, 사업자등록증명의 `정하늘`이 대화 속 `정하늘입니다`에서도 가려진다.
- 사연에는 위 목록과 더해 `○○○ 씨` 앞의 2~3글자 한글도 이름으로 본다(사연에만 나오는 이름 대비).
- 이름 가린 모양: 2글자 `김*`, 3글자 `김*수`, 4글자 `남**희`(첫·끝 글자만 남김). 계약 4.11 예시(`김*수`)·가짜 분석기 값(`박*진`, `이*호`)과 같다.

### 언제·어디서 가리나

1. 분석 ① 단계(`runner._extract_evidence`)에서 서류를 모두 읽은 **뒤**, 이름 목록을 만들고 모든 서류 줄에 `maskedText`를 붙인다. 서류가 늘면 목록이 바뀌므로 **실행마다 사건 전체를 다시 가린다**(글자 처리라 1초도 안 걸림. 이미 읽은 `READY` 서류는 OCR을 다시 하지 않는다).
2. 저장: `evidence.regions_json[].maskedText`, `evidence.masked_text`(가린 줄을 이은 글) — ERD 3.3 그대로, 표 변경 없음.
3. 사연도 같은 목록으로 가려 `out.masked_narrative` → `analysis_runs.masked_narrative`(지금 저장 코드 있음). 가짜 분석 모드에서도 사연은 가린다(서류는 읽지 않으니 숫자 규칙과 `씨` 규칙만 적용). 지금 `scripted.py`가 원문을 넣는 줄을 지운다.
4. 거래상대(`counterparty`) 가리기는 T15(거래 행 추출)가 이 모듈의 `mask_name`을 불러 쓴다. 가짜 분석기는 이미 가린 값(`김*수`)이다.

### 가린 글자 표시 타입

- `app/agent/masking.py`에 `class MaskedText(str)`를 두고 **가리기 함수만 이 타입을 만든다.** 문자열처럼 그대로 저장·비교할 수 있다.
- T16의 `agent/llm.py`는 `MaskedText`가 아닌 값이 들어오면 보내지 않고 오류를 낸다(CLAUDE.md "외부 AI 호출은 llm.py 한 곳, 마스킹 글자만"). T14는 타입과 가리기까지, 막는 검사는 T16.

### 테스트 (`tests/test_t14_masking.py`)

1. 숫자 규칙: 주민번호·휴대폰·사업자번호·계좌가 가려지고, 같은 줄의 날짜·시각·금액·잔액은 그대로
2. 이름 모으기: `예금주 정하늘`·`대표자 정하늘`·거래 행 거래상대 `김민수`는 모으고, `체크카드 결제`·`샘플은행(가상)`은 모으지 않음
3. 사건 이름 목록: 거래내역서에서 모은 이름이 대화 줄(`김민수 (거래처)`, `정하늘입니다`)과 사연에서도 가려짐
4. **완료 조건 테스트:** test01·test02 샘플 서류 글자(텍스트 PDF는 실제 추출, PNG는 생성 스크립트의 줄 목록으로 대신 — 이 PC엔 OCR이 없다)를 가리면, 가린 글에 가상 원문 값(`정하늘` `박서진` `김민수` `한도윤` `이준호` `999-0000-1234-56` `999-0000-5678-90` `123-45-67890` `010-0000-4821`)이 하나도 없음
5. 연결: `AGENT_LLM=claude` 실행 뒤 DB의 `evidence.masked_text`·`regions_json[].maskedText`가 채워지고 원문 이름이 없음, `analysis_runs.masked_narrative`가 가린 사연 (T13 테스트처럼 가짜 OCR 엔진 사용)
6. 가짜 분석 모드에서 사연에 전화번호를 넣고 분석하면 `masked_narrative`에 번호가 가려져 저장되고, 기존 결과(인용 `verified`)는 그대로

이 테스트는 계약 응답 모양을 바꾸지 않는 내부 테스트라 README 계약 테스트 목록에는 넣지 않는다.

### 정할 것 (추천안 먼저)

1. **이름 찾는 방법** — 추천: 위 "사건 이름 목록"(라벨·거래상대 칸에서 모아 사건 전체에 적용). 다른 안: 흔한 성씨로 시작하는 3글자를 모두 가림 → `이번에`·`정말로`·`김치` 같은 말까지 가려져 인용·대조가 망가짐
2. **사업자등록번호** — 추천: 가림(1인 사업자는 사람을 특정함, AI 대조엔 필요 없음). 계약 1절 목록엔 없지만 더 가리는 쪽이라 계약 변경 불필요
3. **상호(`하늘가죽공방`)** — 추천: 안 가림(사람 이름이 아니고, 대화 속 "하늘가죽공방 맞죠?"가 거래 사실 대조에 쓰임)
4. **계좌·전화의 남길 자리** — 추천: 끝 4자리 남김(같은 계좌인지 AI가 구별할 수 있게). 다른 안: 전부 `*`
5. **OCR이 이름을 잘못 읽은 경우**(예: `김민수`→`김민슈`) — 추천: 이번엔 처리 안 함, Docker OCR로 샘플 PNG를 가려 원문 이름이 남는지 한 번 확인(시연은 합성 서류라 남아도 실제 개인정보 아님). 남으면 결과에 적고 T19에서 판단

## 결정

11/22 사용자 확인("응"): 정할 것 1~4는 추천안. 5는 수정안으로 정함.

1. 이름은 사건 이름 목록 방식. 라벨은 `예금주`·`대표자`·`성명`만 쓴다. `이름`은 "이름을 알려 주세요" 같은 문장에서 다른 말을 이름으로 잡을 수 있어 뺐다. 라벨과 이름 사이에는 공백이나 `:`가 있어야 한다
2. 사업자등록번호는 가린다
3. 상호는 가리지 않는다
4. 계좌·전화는 끝 4자리만 남긴다
5. 이름은 띄어쓰기를 무시하고 찾는다(`김 민수`도 가림). 라벨 뒤 공백이 여러 칸이어도 찾는다. OCR이 칸 사이를 공백 여러 칸으로 읽기 때문이다(`대표자                    정하늘`). 한 글자 틀리게 읽은 이름(`김민슈`)은 처리하지 않고 남은 위험으로 적는다
   - 근거: Docker OCR(`proofy-ocr-check`)로 샘플 PNG 3개를 읽어 보니 이름·번호가 모두 정확했다(`김민수 (거래처)`, `샘플은행 999-0000-1234-56 정하늘입니다`, `대표자 … 정하늘`, `123-45-67890`, `010-0000-4821`). 틀리게 읽힌 줄은 이름이 없는 "합성 데이터" 띠 줄뿐이었다

## 결과

- 사연 `씨` 규칙: `김민수 씨에게`처럼 조사가 붙어도 잡는다. `아저씨`·`아가씨`·`마음씨`는 제외

- Docker OCR 확인(`proofy-ocr-check`): test01·test02 샘플 5개를 실제로 읽고 가린 결과 가상 원문 값 9개가 하나도 남지 않음. 가린 예: `김*수 (거래처)`, `샘플은행 ***-****-**34-56 정*늘입니다`, `대표자 정*늘`, `등록번호 ***-**-*****`, `010-****-4821`

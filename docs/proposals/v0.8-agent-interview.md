# 계약 v0.8 제안 — 인터뷰형 에이전트(AI 의견·질문·답변)

- 작성: 2026-11-22 · 상태: **제안(FE 확인 전).** FE가 받기로 하면 `docs/contract.md`에 반영하고 변경 이력에 적는다
- 기준 FE: `proofy-ai/proofy-fe` main `8f56fb2`(11/22 03:44)

## 1. 왜 바꾸나

지금 에이전트는 "자료를 넣으면 결과가 나오는" 한 번짜리다. 사용자와 주고받는 부분이 없다.
바꾼 뒤에는 에이전트가 **법령을 직접 찾아 읽고(RAG), 근거를 댄 조건부 의견을 내고, 부족한 사실을 되묻는다.**
사용자가 답하면 그 답을 반영해 다시 대조·초안을 만들고 또 묻는다.

```
사연 + 서류 → 에이전트(거래내역 조회 · 법령 조회 · 스스로 점검)
           → 결과: 대조 + 초안 + ★AI 의견(근거 조항 인용) + ★질문 2~3개
           → 사용자가 답함("저는 이 경우가 아니라 ~ 상황이에요"도 여기에)
           → 답을 반영해 다시 분석 → 또 질문 …
```

### 지키는 선(원칙 1을 이렇게 바꾼다)
| 한다 | 하지 않는다 |
|---|---|
| "말씀하신 내용과 올린 자료를 기준으로 보면 ~로 설명할 수 있는 사정으로 보입니다"처럼 **조건부 의견** | "해제될 것이다", "가능성이 높다" 같은 **결과 예측** |
| 법령·별지 서식을 **원문 인용**으로 근거 제시(서버가 원문에 있는지 확인) | 없는 조항 인용(확인 안 되면 "확인 필요"로 표시) |
| 부족한 사실을 **질문** | AI 의견을 **소명서 본문에 넣기**(소명서는 본인 사실 진술만) |
| 위험한 표현이 있으면 근거를 들어 **상담 권유** | 사람을 범죄자로 판정 |

가리기(대회 규정 제7조), 금액·날짜 코드 계산, 인용 검증은 그대로다.

## 2. FE가 할 일 — 새로 만들기 vs 고치기

**새 화면·새 탭은 없다.** 결과 화면(5번)에 카드 하나를 끼워 넣고, 이미 있는 "다시 분석" 흐름에 답변을 실어 보내면 된다.

### 새로 만들 것
| 무엇 | 내용 |
|---|---|
| `AgentReviewCard` 컴포넌트 | ① AI 의견 목록(각 의견 아래 근거 조항 칩: `label` + 펼치면 `quote`, `verified:false`면 흐리게, `needsCheck`면 "확인 필요") ② 질문 목록(질문 + `why` 작은 글씨 + 답 입력칸) ③ "답하고 다시 분석" 버튼 ④ 이전에 답한 내용(`answered`, 접힘) ⑤ 맨 아래 `notice` 문구 |
| 타입 | `AgentReview`, `AgentOpinion`, `AgentQuestion`, `LawRef`(4절), `AnalysisStart.answers` |
| 목 데이터 | GOODS·UNEXPECTED 결과에 `agentReview` 추가(4절 예시 그대로 써도 됨) |

### 고칠 것
| 파일 | 바꿀 점 |
|---|---|
| `components/ResultView.tsx` | `ResultHeader`·`ResultBanners` 아래, 탭 위에 `<AgentReviewCard>`. **`referral`이 있을 때도** `ReferralCard` 아래에 보여 준다(상담 권유를 받은 사람도 질문에 답해 다시 분석할 수 있게) |
| `hooks/useAnalysisRetry.ts` | `mutationFn`이 `answers`도 받아 `startAnalysis(caseId, caseToken, { overwriteEditedDraft, answers })`로 보냄. `DRAFT_HAS_EDITS` 확인창 흐름은 그대로 |
| `types/api.ts` | `AnalysisResult.agentReview: AgentReview \| null` 추가, `AnalysisStart.answers?` 추가 |

### 그대로인 것
1~4번 화면, 탭 A(증빙 대응표)·B(부족한 서류)·C(소명서 초안), 진행 화면(step `type` 값 추가 없음, 법령 조회는 `TOOL_CALL`), `ReferralCard`(문구는 서버가 줌), 오류 코드 목록.

## 3. API 변경

### 3.1 `POST /cases/{caseId}/analysis-runs` — `answers` 추가(선택)
```json
{
  "narrative": "…",
  "overwriteEditedDraft": false,
  "answers": [
    { "questionId": "q1…", "answer": "처음엔 3개였는데 다음 날 1개를 더 주문받아 15만 원이 됐어요." }
  ]
}
```
- `questionId`는 **가장 최근 성공 결과의 `agentReview.questions`**에 있는 것만. 아니면 `400 VALIDATION_ERROR`(`details.fields.answers`)
- `answer`는 1~500자. 빈 답은 FE가 빼고 보낸다(답하지 않은 질문은 보내지 않음)
- 서버는 답을 사건에 저장한 뒤(사연처럼 먼저 저장) 사전 조건 검사·분석을 시작한다. 답이 있으면 `inputVersion` +1(그래서 샘플 "그대로" 조건은 깨진다)
- 다음 분석에서 에이전트는 사연과 **지금까지의 모든 질문·답**을 함께 본다(가린 글). 답은 사용자 진술이라 근거 종류는 기존 `NARRATIVE`로 나온다(FE 변경 없음)

### 3.2 `GET /cases/{caseId}/result` — `agentReview` 추가
`agentReview`는 실제·가짜·미리 만든 결과 모두 채운다. 분석이 질문을 하나도 만들지 않으면 `questions: []`.

### 3.3 상담 안내(`referral`) 규칙 변경 — 모양은 그대로
| | 지금(v0.6.5) | 바뀐 뒤 |
|---|---|---|
| 누가 정하나 | 정해 둔 표현 목록(코드) | 실제 AI 분석: 코드 목록이 찾은 표현을 AI에 넘기고, **AI가 문맥을 읽어**("빌려준 적 없다" 같은 부정문 구분) 상담을 권할지 정한다. 권하면 사연 원문을 인용해야 하고 서버가 인용을 확인한다. 가짜·미리 만든 결과는 코드 목록(부정문 규칙 포함)만으로 |
| AI 호출 | 안 함 | 함 |
| 결과 | `findings: []`, `draft: null` | 같음 + **`agentReview`에 질문이 있음**(예: "통장을 건넨 상대와 목적을 알려 주세요"). 답하고 다시 분석하면 상담 권유가 풀릴 수 있다 |
| `matchedPhrases` | 코드가 찾은 글자 | 서버가 확인한 인용(사연 원문 글자) |

## 4. 응답 모양

```json
"agentReview": {
  "notice": "올린 자료와 말씀하신 내용을 기준으로 AI가 정리한 의견입니다. Proofy는 변호사가 아니며, 지급정지 해제 여부는 은행이 판단합니다.",
  "opinions": [
    {
      "opinionId": "o1…",
      "text": "말씀하신 내용과 거래내역을 기준으로 보면, 11월 8일 150,000원 입금은 물품 대금으로 받은 돈이라고 설명할 수 있는 사정으로 보입니다.",
      "findingIds": ["f1…"],
      "lawRefs": [
        {
          "source": "LAW",
          "label": "법 제7조 제1항 제2호",
          "quote": "재화 또는 용역의 공급에 대한 대가로 받았거나",
          "verified": true
        }
      ],
      "needsCheck": false
    }
  ],
  "questions": [
    {
      "questionId": "q1…",
      "text": "대화에서는 '3개 12만원'으로 이야기했는데 입금은 15만 원입니다. 금액이 달라진 이유가 있나요?",
      "why": "자료와 어긋난 금액은 은행이 설명을 요청할 수 있습니다.",
      "findingIds": ["f2…"],
      "lawRefs": []
    }
  ],
  "answered": [
    { "questionId": "q0…", "text": "…", "answer": "…", "answeredAt": "2026-11-22T06:45:41Z" }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `opinions` | 0~3개. AI의 조건부 의견. `findingIds`는 같은 결과의 대조 항목(탭 A로 이동에 쓸 수 있음) |
| `opinions[].needsCheck` | 서버 검사에서 걸림: 근거 조항 인용이 원문에 없음, 결과를 예측하는 표현, 근거 없는 금액·날짜. FE는 초안의 "확인 필요"와 같은 표시 |
| `lawRefs[].source` | `LAW` 통신사기피해환급법 · `DECREE` 같은 법 시행령 · `FORM4` 별지 제4호 서식 |
| `lawRefs[].label` | 화면에 보일 이름(예: "법 제13조의2 제1항"). 서버가 원문 목록에서 붙인다 |
| `lawRefs[].verified` | `quote`가 법령 원문에 실제로 있나(서버가 확인). `false`면 흐리게 |
| `questions` | 0~3개. 답 입력칸을 하나씩 |
| `answered` | 이 사건에서 지금까지 답한 질문(오래된 것부터). 화면에 접어서 보여 주면 대화가 이어지는 느낌이 난다 |

**판정 필드는 여전히 없다.** `releasable`·`probability`·`verdict` 같은 필드는 두지 않고, 의견 문장에 결과 예측 표현이 있으면 서버가 고쳐 쓰게 하거나 `needsCheck`로 표시한다.

## 5. BE가 할 일(참고, 약 7시간)
1. 법령 조회 도구: `docs/legal/` 법률·시행령·별지 제4호를 조항 단위로 나눠 AI가 검색·조회(도구 호출, 진행 화면에 `TOOL_CALL` "법령 조회"). 인용 검증
2. 에이전트 출력에 의견·질문 추가 + 서버 검증(인용, 결과 예측 표현, 숫자)
3. 답변 저장·검증·다음 분석에 반영(가린 뒤 AI로). 새 표 `agent_reviews`·`case_answers`(새 표만 추가라 배포 DB 초기화 불필요)
4. 상담 안내를 AI 문맥 확인 + 코드 목록 바닥망으로
5. 가짜 분석·미리 만든 결과에도 고정 `agentReview`
6. CLAUDE.md 원칙 1, `docs/agent-design.md`, 판정 필드 부재 테스트(T16-a) 고치기

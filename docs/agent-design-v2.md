## 💡 0. 한 줄 요약

**AI는 판사가 아니라, 계획을 세워 직접 조사하고 근거를 대며 묻는 정리 담당이다.**

사연과 올린 서류를 맞대어 "자료와 맞음 / 어긋남 / 자료 없음"으로 정리하고, 법령을 찾아 읽어 근거를 댄 조건부 의견을 내고, 부족한 사실을 묻는다. 사용자가 답하면 지난 분석을 돌아보고 계획을 고쳐 다시 정리한다. 해제될지는 말하지 않는다. 숫자·날짜·기한은 코드가 만들고, AI가 쓴 것은 코드가 다시 검증한다.

역할 범위(이의제기 5단계 중 2단계 "소명 자료 준비")와 초안 3묶음(입금 경위·가담 안 함·피해 경위)은 v1 1절 그대로다.

## 🧩 1. 에이전트 4요소

### 🗺️ 계획
- ② 대조를 시작할 때 AI가 확인할 주장과 각각 볼 자료를 먼저 정한다(`make_plan`)
- 조사 중 필요하면 한 번 고친다
- 다시 분석할 때는 지난 분석과 사용자 답을 보고 무엇을 바꾸는지 밝힌다
- 코드는 끝에 계획 대비 결과를 점검한다
- **화면:** 4번 화면 "조사 계획", "조사 계획 수정" 줄, `VERIFY` "계획한 확인 3개 중 3개"

### 🔧 실행
- 생각(조회 이유) → 행동(도구) → 관찰(결과)을 반복하는 도구 루프(최대 12회)
- 결과는 코드가 검증하고, 걸린 문장·의견은 AI가 1회 고쳐 쓴다
- **화면:** 4번 화면 조회 줄마다 AI가 밝힌 이유, `VERIFY` 줄

### 🧰 도구
- 조사 계획, 거래내역 조회, 서류 글 조회, 법령 검색, 조항 읽기 5개
- 거래·서류 도구는 이 사건 것만 돌려준다
- **화면:** 4번 화면 `TOOL_CALL` 줄

### 🧠 기억
- 단기: 한 분석 안의 대화 이력
- 단계 사이: 대조 결과를 초안·검증에 넘김
- **사건 단위: 지금까지의 질문·답과 지난 분석의 성찰 거리를 DB에 두고 다음 분석마다 넘김**
- 다른 사건·사용자의 기억은 두지 않는다(개인정보, 24시간 삭제)
- **화면:** 5번 화면 "이전에 답한 내용", 다시 분석 때 "조사 계획 수정" 이유

## 🧪 2. 계획과 의사결정 기법

분류는 Lilian Weng, "LLM Powered Autonomous Agents"(2023)를 따른다. 계획 = 작업 분해 + 자기 성찰.

### 쓰는 기법

- **CoT (사고의 연쇄)** — T24
  - 뜻: 단계별로 생각해 문제를 쪼갬
  - Proofy: 큰 단계(읽기 → 대조 → 초안 → 검증)는 코드가 쪼개고, ② 안에서는 AI가 조사 계획으로 주장 단위로 쪼갠다. 계획이 화면에 드러난다
- **ReAct** — T16·T23
  - 뜻: 생각 → 행동 → 관찰 반복
  - Proofy: ② 도구 루프. 도구마다 `reason`(생각)이 필수 인자이고 화면에 보인다
- **Reflexion** — T17·T24, T25
  - 뜻: 실패를 언어로 되돌아보고 기억해 다음 시도에 반영
  - Proofy ① 한 분석 안: 코드가 검증에서 찾은 오류(근거에 없는 숫자, 결과 예측 표현)를 사유와 함께 돌려주면 AI가 1회 고쳐 쓴다(초안·의견)
  - Proofy ② 분석 사이: 다시 분석할 때 지난 분석의 어긋남·확인 못 함·검증에 걸린 것을 넘기고, AI가 계획을 고친 이유를 밝힌다
- **과거 행동 성찰** — T25
  - 뜻: 이전 실행을 돌아봄
  - Proofy: Reflexion ②와 같다. 사용자 답은 사람의 피드백으로 함께 들어간다

### 쓰지 않는 기법

- **ToT (사고의 나무):** 여러 갈래를 펼쳐 평가하고 고르는 기법. 호출이 몇 배로 늘어 150초 마감·비용에 맞지 않고, 우리 문제는 정답 탐색이 아니라 사실 확인이라 갈래를 늘리기보다 코드 검증이 효과적이다
- **LLM+P:** 외부 계획기에 맡기는 기법. 흐름이 짧고 정해져 있어 필요 없다
- **CoH (Chain of Hindsight):** 피드백이 달린 출력 이력으로 모델을 **미세조정**하는 학습 기법. 우리는 API로 모델을 쓰므로 해당 없다

### 의사결정: 무엇을 AI가 정하고 무엇을 코드가 쥐나

"탐색은 자유, 결과는 엄격"(11/22). 코드는 AI가 **지어낸 것**만 걸러 낸다.

**AI가 정한다**
- 사연에서 확인할 주장, 조사 순서(계획)
- 어느 도구를 어떤 조건으로 몇 번 부를지, 언제 멈출지(상한 12회)
- 계획을 중간에 고칠지(1회)
- 무엇이 부족해 사용자에게 물을지

**AI가 정하고 코드가 확인한다**
- 일치·어긋남·진술만·확인 못 함 → 코드가 근거 확인(근거 없는 일치는 확인 못 함으로)
- 어떤 법령 조항을 읽고 어떤 의견을 낼지 → 코드가 인용을 원문과 대조
- 상담으로 넘길지(코드 표현 목록이 후보를 줌) → 코드가 인용 확인

**코드가 정한다**
- 단계 순서, 마감, 호출 상한
- 금액·날짜·기한·체크리스트 충족, 인용 진위, 같은 사건 소속

**아무도 정하지 않는다**
- 해제 가능성·수용 여부(스키마에 칸이 없다)

## 🔄 3. 흐름

```text
POST /analysis-runs (202, answers가 있으면 검증 후 저장)
  → 백그라운드 실행, 마감 150초
  ① EXTRACTING  [코드]  글자 추출 → 마스킹(서류 줄, 사연, 질문·답) → 거래 행(규칙)
  ⓪ SAFETY      [코드]  상담 안내 표현 찾기(부정문 제외) → ②에 "확인할 표현"으로 넘김
  ② COMPARING   [AI 도구 루프]
       계획     make_plan: 확인할 주장 + 볼 자료 (다시 분석이면 지난 분석·답을 보고 고친 점)
       ReAct    get_transactions · get_evidence_regions · search_law · get_law_article (이유 필수)
       (필요하면 make_plan으로 계획 수정 1회)
       출력     findings · 권장 자료 · 의견 · 질문 · 상담 권유 여부
     [코드]    근거 확인(조회한 거래만, 같은 사건 서류만, 인용 원문 대조, 법령 인용 대조),
               계획 대비 점검
  ③ DRAFTING    [AI 1회]  findings와 답만으로 초안(상담 권유면 건너뜀)
  ④ VERIFY      [코드 → AI 1회 → 코드]  초안 문장·의견 검사 → 고칠 수 있는 것만 1회 고쳐 쓰기 → 재검사
  ⑤ 결과        → 사용자가 질문에 답하고 "답하고 다시 분석"
                 → 처음부터 다시(답 + 지난 분석 성찰 거리를 ②에 넘김)
```

화면 단계(`stages`)는 ①·②·③ 세 개다. ⓪은 ①에, ④는 ③에 포함해 보여 준다. 각 단계에서 한 일은 `steps`에 한 줄씩 남는다(계약 4.10). 새 step 종류는 없다: 조사 계획·법령 조회는 `TOOL_CALL`, 계획 대비 점검은 `VERIFY`.

## 🛠️ 4. 단계별 설계

### 4.1 ① 글자 추출·마스킹·거래 행 (T13·T14·T15, 코드)

v1 2.2·2.3 그대로. AI에는 마스킹한 글자만 간다(원칙 4, `MaskedText` 타입만 `agent/llm.py`가 받음). 인용 검증 기준도 마스킹본이다. **v0.8부터 질문·답도 같은 사건 이름 목록으로 가린다.**

### 4.2 ⓪ 상담 안내 (T10)

v1 2.1 그대로.

- 코드 표현 목록(4묶음)은 분석 시작 때 서비스 계층이 원문 사연·답으로 찾는다
- **코드는 후보만 찾고 판단하지 않는다(11/22 결정)**
  - 실제 분석은 부정문까지 포함한 후보 전부를 runner가 가려서 ②에 넘긴다
  - 부정문을 뺀 목록은 AI가 없는 곳(가짜 분석·미리 만든 결과, AI 인용이 원문에 없을 때 대신 보여 줄 표현)에서만 쓴다
- 실제 분석은 AI가 문맥으로 정하고 사연·답 원문을 인용하며, 서버가 인용을 확인한다
- 상담 안내로 끝나면 대조·초안·의견 없이 `referral` + 상황을 묻는 질문만 남기고 이전 초안을 지운다
- 가짜 분석·미리 만든 결과는 표현 목록만으로 정한다

### 4.3 ② 대조 — 계획 + ReAct (T16·T23·T24)

#### 도구

- **`make_plan`** (T24)
  - 인자: `items[] {claim, check, sources[]}`(최대 6, `sources` ⊂ `TRANSACTIONS`·`EVIDENCE`·`LAW`), `revision`(바꾼 점 한 문장 또는 null)
  - 돌려주는 것: 받았다는 확인
  - 화면 줄: "조사 계획"(두 번째는 "조사 계획 수정"). 예) `확인할 것 3가지: 11/8 입금(거래내역) · 합의 금액(대화내역) · 이의제기 사유(법령)`. `revision`이 있으면 앞에 붙임
- **`get_transactions`**
  - 인자: `reason`, `from`, `to`, `direction?`, `counterparty?`, `minAmount?`, `maxAmount?`
  - 돌려주는 것: 이 사건 거래 행(상대 이름은 가림)
  - 화면 줄: "거래내역 조회" `{이유} → N건`
- **`get_evidence_regions`**
  - 인자: `reason`, `evidenceId`, `page?`
  - 돌려주는 것: 이 사건 서류의 줄(가림)
  - 화면 줄: "○○ 글 조회" `{이유} → N줄`
- **`search_law`** (T23)
  - 인자: `reason`, `query`
  - 돌려주는 것: 낱말이 맞는 조항 5개 `{ref, label, title, snippet}`
  - 화면 줄: "법령 조회" `{이유} → 조항 N개(…)`
- **`get_law_article`** (T23)
  - 인자: `reason`, `ref`
  - 돌려주는 것: 조항 원문
  - 화면 줄: "법령 조회" `{이유} → 법 제7조`

도구 규칙

- `make_plan`은 첫 호출로 쓰게 한다(프롬프트). 호출 상한(12회)에 세지 않고 실행당 2번까지(처음 + 수정 1회). 강제 `tool_choice`는 쓸 수 없다(adaptive thinking에서 400). 계획 없이 조사하면 계획 줄 없이 진행한다
- 법령은 공개 글이지만 보낼 때 `MaskedText`를 거친다. 법령 원문은 `app/agent/law_data/`, 조 단위로 나눈다(부칙 제외, 별지 제4호는 한 조각). 서버는 이번 실행에서 돌려준 조항 `ref`를 모아 두고 의견·질문의 근거 조항을 그 원문과 대조한다
- 상한: 도구 12회, 모델 요청 14회, 도구 결과 60,000자. 넘으면 지금까지 본 자료로 답하게 한다

#### 첫 메시지

- 사연(가림)
- 지금까지의 질문·답(가림, T25)
- **지난 분석 성찰 거리(T25, 4.6)**
- ⓪이 찾은 확인할 표현(T10)
- 사용자가 말한 입금(유형·금액·일자)
- 서류 목록(앞부분 몇 줄)
- 이 유형의 고정 체크리스트

#### 최종 출력 (구조화, `output_config.format`)

```text
findings[]        = { claim, status, note, conflict | null, sources[], planItem | null }
recommendedDocs[] = { label, reason, acceptedDocTypes[] }                  (0~3)
opinions[]        = { text, findingIndexes[], lawRefs[]: { ref, quote } }  (0~3, T24)
questions[]       = { text, why, findingIndexes[], lawRefs[] }             (0~3, T24)
consult           = { recommend, quotes[], reason }                        (T10)
```

- **판정 필드는 스키마에 없다**(해제 가능성, 수용 여부, 위험도). 계약 테스트 T16-a가 칸 목록을 고정한다
- `planItem`은 그 주장이 계획의 몇 번 항목을 확인한 것인지(0부터). 계획 대비 점검에 쓴다

#### 코드 검증 (저장 전)

- **거래 근거가 이번 실행에서 도구가 돌려준 ID인가**
  - 아니면 그 근거를 빼고 `VERIFY`
- **서류 근거가 이 사건 서류의 실제 줄인가**
  - 아니면 그 근거를 빼고 `VERIFY`
- **인용이 마스킹한 서류 줄·사연·답에 있나**(공백 무시)
  - 없으면 `verified: false`(흐리게, 지우지 않음)
- **자료 근거 없는 일치·어긋남**
  - `UNKNOWN`으로
- **의견·질문의 근거 조항이 이번 실행에서 읽은 조항이고 인용이 그 원문에 있나**
  - 아니면 `verified: false`, 의견은 `needsCheck`
  - 찾으면 항·호까지 label("법 제7조 제1항 제2호")
- **의견·질문의 `findingIndexes`가 있는 항목인가**
  - 없는 번호는 버림
- **계획 대비 점검:** 계획 항목마다 `planItem`이 그 번호인 주장이 있나
  - 출처가 법령뿐(사연은 곁들여도 됨)인 항목은 의견·질문에 확인된(`verified`) 법령 인용이 있으면 마친 것으로 센다(#73: 법령 확인은 대조 항목이 아니라 `lawRefs`로 나오기 때문)
  - 조항을 읽기만 한 것은 세지 않고, 거래내역·서류가 섞인 항목은 `planItem`으로만 센다
  - 결과는 `VERIFY` "계획한 확인 3개 중 2개를 마쳤습니다. 확인 못 한 것: …"
  - 확인 못 한 항목을 질문으로 돌리는 것은 AI에 맡긴다(프롬프트가 확인 못 한 항목은 질문하게 함)
- **글자 수 상한**
  - 넘으면 자름

### 4.4 ③ 초안 (T17)

v1 2.5 그대로.

- 입력은 검증을 통과한 findings와 **질문·답(T25)**. 답의 사실도 본인 진술로 쓴다
- 근거 번호는 enum으로 묶는다
- **의견은 초안에 넣지 않는다**(초안은 본인 사실 진술)

### 4.5 ④ 검증과 1회 고쳐 쓰기 — 한 분석 안의 Reflexion (T17·T24)

- **초안 문장**
  - 검사: 어긋남 연결(`CONFLICT`), 근거 없음(`NO_SOURCE`), 인용 못 찾음, 숫자 불일치(`NUMBER_MISMATCH`), 판정 표현(`JUDGMENT_EXPRESSION`), 근거 서류 못 읽음
  - 고쳐 쓰기: 숫자·판정 표현만
- **의견**
  - 검사: 법령 인용 못 찾음, 결과 예측·확정 표현("해제될", "가능성이 높", "해당합니다"), 근거에 없는 금액·날짜
  - 고쳐 쓰기: 예측 표현·숫자만
- **질문**
  - 검사: 근거 조항 대조만(`verified`)
  - 고쳐 쓰지 않음(묻는 문장이라 단정하지 않음)

고쳐 쓰기 규칙

- 초안 문장과 의견을 **한 번의 고쳐 쓰기 호출**에 같이 넣는다(호출 수 그대로). 마감까지 40초 이상 남았을 때만
- 다시 검사해 통과하면 고친 글, 또 걸리면 **원래 글을 두고 "확인 필요"**. 지우지 않는다(원칙 3)
- 고칠 수 없는 사유(근거 없음, 인용 못 찾음, 어긋남)는 AI에 돌려주지 않는다. 고치게 하면 근거를 지어낼 수 있다

### 4.6 ⑤ 질문 → 답 → 다시 분석 — 기억과 분석 사이의 Reflexion (T24·T25)

**질문:** AI가 정한다. 이미 답한 질문은 다시 묻지 않는다. 주로 묻는 것은
- 어긋난 항목의 설명
- 진술만 있는 항목의 자료
- 별지 제4호 사유에 필요한데 사연에 없는 사실
- 계획했지만 확인 못 한 항목
- 상담 권유 때 상황

**답 받기**
- `questionId`는 가장 최근 성공 실행의 질문만, 1~500자
- 검증을 모두 통과해야 사연·답을 저장한다(반만 반영되지 않게)
- 저장하면 `inputVersion` +1

**다시 분석할 때 ②에 넘기는 것**
- **지금까지의 질문·답(가림)**
  - 출처: `analysis_questions`
  - 역할: 사람의 피드백. 답은 사용자 진술로 `NARRATIVE` 근거가 될 수 있고 인용 검증 기준에 붙는다
- **지난 분석 성찰 거리(가림)**
  - 출처: 가장 최근 성공 실행
  - 내용: 어긋난 항목·확인 못 한 항목·진술만 있는 항목(claim·status·note), 계획했지만 확인 못 한 항목, 확인 필요 문장 수·의견 수

넘긴 뒤의 규칙

- AI는 `make_plan`의 `revision`에 "지난 분석에서 금액이 어긋났고, 답에서 추가 주문을 말씀하셔서 추가 주문 대화를 다시 확인합니다"처럼 **무엇을 왜 바꾸는지** 쓴다. 화면 "조사 계획" 줄 앞에 붙는다
- 새 표는 없다. 성찰 거리는 이미 저장된 지난 실행의 findings·초안·의견에서 서비스가 모은다
- 매번 처음부터 다시 분석한다(실시간 대화가 아니다). 단계마다 같은 검증을 거치므로 답 때문에 검증이 느슨해지지 않는다

### 4.7 가짜 분석(`scripted`)과 미리 만든 결과

시나리오별 고정 결과(계약 4.11·7절).

- 조사 계획 줄, 법령 조회 줄, 의견 1개·질문 2개를 정해 둔 값으로 낸다
- 답한 질문은 다시 내지 않고, 다시 분석이면 계획 줄에 고정 `revision`("지난 분석과 답변을 보고 다시 확인합니다")을 붙인다
- 상담 안내는 표현 목록만으로 정한다
- 샘플 사건이 AI 실패·하루 한도 초과면 이 결과로 대체한다(`precomputed`, step `FALLBACK`)

## 🎬 5. 화면에 보이는 장면 (test01, 시연 대본의 뼈대)

**1회차** — 4번 화면 진행 기록

```text
[조사 계획]       확인할 것 3가지: 11/8 입금(거래내역) · 합의 금액(대화내역) · 이의제기 사유(법령)   ← 계획(CoT)
[거래내역 조회]   사연의 11월 8일 대금 입금을 확인하려고 11/1~11/10 입금 조회 → 2건            ← ReAct
[대화내역 글 조회] 합의한 금액을 확인하려고 → 34줄                                           ← ReAct
[법령 조회]       물품 대금이 이의제기 사유가 되는지 확인하려고 → 법 제7조                       ← ReAct + RAG
[자료와 어긋남]   대화의 합의 금액(120,000원)이 사연·입금액(150,000원)과 다릅니다
[계획 점검]       계획한 확인 3개를 모두 마쳤습니다                                            ← 계획 대비 점검
[초안 확인]       근거와 다른 숫자 1개를 AI가 고쳐 다시 확인했습니다                             ← Reflexion(안)
```

5번 화면 AI 의견·질문 카드

- 의견: "말씀하신 내용과 거래내역을 기준으로 보면 … 설명할 수 있는 사정으로 보여요" + 칩 `법 제7조 제1항 제2호`
- 질문: "대화에선 12만 원인데 입금은 15만 원이에요. 금액이 달라진 이유가 있나요?"

**2회차** — 답 "다음 날 1개를 더 주문받아 4개 15만 원이 됐어요" → 답하고 다시 분석

```text
[조사 계획]  지난 분석에서 금액이 어긋났고 답에서 추가 주문을 말씀하셔서 추가 주문 대화를 다시 확인합니다
             → 확인할 것 3가지: …                                                       ← 기억 + Reflexion(사이)
```

5번 화면

- 초안에 "이후 1개를 추가 주문받아 15만 원이 되었습니다"(본인 진술)
- 같은 질문은 "이전에 답한 내용"으로

**FE 변경**

- 진행 기록은 지금 화면(`AnalysisProgressPanel`, 최근 3줄)에 그대로 나온다
- 계획 줄을 위에 고정하는 것은 선택(FE)
- 의견·질문 카드는 계약 v0.8 FE 작업

- 이 한도는 파라미터로 늘릴 수 없고 출력 스키마가 이미 한도 가까이에 있다. 스키마 칸이나 strict 도구를 늘릴 때는 `scripts/check_claude_schema.py`로 실제 API에서 먼저 확인한다

**호출 수(실제 분석 1회)**

- ② 대조 요청 4~8회(계획 1 + 조회 + 최종)

## ⚠️ 8. 한계와 대응 (소개서 "AI 결과의 한계")

v1 7절에 더한다.

- **AI가 계획만 세우고 확인하지 않음**
  - 코드가 계획 대비 결과를 점검해 화면에 남기고, 확인 못 한 항목은 질문으로 묻게 한다
- **지난 분석의 잘못된 판단이 다음 분석에 굳어짐**
  - 성찰 거리는 "무엇이 어긋났고 무엇을 못 확인했나"만 넘기고 결론은 넘기지 않는다
  - 매번 자료를 다시 조회하고 같은 검증을 거친다
- **계획을 세우는 데 시간·비용이 듦**
  - 요청 1회. T19 실측에서 150초 안에 드는지 확인하고, 길면 계획 수정(2번째 호출)을 막는다

## 🤔 10. 왜 이 형태인가

v1 3절에 더한다.

- **계획을 드러냈다.** 계획이 보이지 않으면 사용자와 심사자가 AI가 무엇을 하려 했는지 알 수 없고, 코드가 "계획했지만 안 한 것"을 잡을 수 없다
- **성찰은 결론이 아니라 빈 곳만 넘긴다.** 지난 결과를 통째로 넘기면 AI가 그대로 베껴 같은 실수를 반복할 수 있다. 어긋남·확인 못 함만 넘기고 자료는 다시 조회하게 했다
- **ToT·멀티 에이전트는 쓰지 않는다.** 150초 안에 끝나야 하고 건당 비용이 제한돼 있다. 정답이 여러 갈래인 문제가 아니라 자료와 맞는지 확인하는 문제라, 갈래를 늘리는 것보다 검증이 낫다
- 프레임워크(LangGraph) 없이 직접 짠 이유는 v1 3절 그대로
